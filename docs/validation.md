# FineTune-Rewrite 検証方針

## 対象と位置付け

[アーキテクチャ設計案](<architecture.md>)を検証するための試験対象・方法・確認条件を扱う。
初期の設計案に基づく方針であり、試験の実装状況や検証結果を示すものではない。
実行可能なテストとその手順・現在の検証範囲は[README](<../README.md>)、互換性の参照基準は[開発ガイド](<../AGENTS.md>)を参照する。

## 試験対象

| 対象 | 確認すること |
| --- | --- |
| Domain | 希望の保持、経路選択、音量の意味・変換 |
| Control | 古い準備完了、連続した変更要求、有効化失敗、終了処理 |
| 互換性 | 旧設定の意味、URLの解釈、UIと外部操作の結果の一致 |
| AudioDSP | 片側だけの入力、短い信号、無音からの復帰、機器別補正、処理履歴の独立 |
| native公開境界 | エラー処理、部分的な作成失敗、資源の所有と回収 |
| 実機の音声経路 | tap・aggregate・チャンネル対応、切り替え、切断、フォーマット変更 |
| UI | 主要な操作経路と表示 |

音量の具体的な変換式や旧設定の解釈は、比較対象の実装と互換テストで確認する。
実装に着手する際は、比較対象の版と期待結果を確認してから、それぞれの受け入れ条件を追加する。

## 検証方法と実行条件

- Domainの判断、Controlの非同期処理、DSPの信号処理は、UIや実機なしで検証する。
  Controlでは、切断・準備失敗・古い要求の遅延完了を再現する。
- 機器との接続・切り替えは、本番のNativeAudioを利用する小さな検証用プログラムで観測する方針とする。
- Swiftのテスト、C++の信号試験、実機試験は実行条件を分ける。
- リアルタイム検査ツールは採用するコンパイラとruntimeでの利用可否を確認してから選び、導入済みとは扱わない。
- 性能は実装して計測する。言語変更だけを性能改善の証拠にしない。

## 音声経路の実機検証

初期の設計案では、出力チャンネルを明示的に扱うaggregate構成を先に検証し、必要な機器の組み合わせを扱えなければ出力を独立させる方式を検討する案が示されている。
方式選択のため、少なくとも次の条件を確認する。

- 1アプリから複数機器へ、それぞれのEQ・補正を独立して適用できるか。
- 切り替え・切断・フォーマット変更時にも、経路と処理状態の整合性を保てるか。
- 初音に必要な音量・補正を適用することと、idle時の消費・スリープを両立できるか。

## 結果の扱い

UI試験やビルド成功を、音声の正しさ・リアルタイム安全性の証拠にしない。
開発用の仮置きや設計上の期待も、確認条件が成立した証拠にしない。
ビルド可能なOSと実機で確認したOSを区別する。具体的な環境・設定値は[README](<../README.md>)と[ビルド設定](<../Package.swift>)で確認する。

方式を選ぶ際は、採用条件・結果・未検証の範囲を記録し、[設計案](<architecture.md>)との差を明示する。
